# Свой сервер UNYRI: Windows, домашний ПК или VPS

## Вы — оператор своего сервера

Установив сервер, вы становитесь его оператором: вы отвечаете за сервер, его пользователей и их данные, обновления и резервные копии, правила, работу с жалобами и соблюдение закона там, где сервер работает (например, за политику конфиденциальности для ваших пользователей). Разработчик UNYRI не управляет вашим сервером, не имеет к нему доступа и не отвечает за него. Программа предоставляется «как есть», без гарантий (AGPL-3.0).

## Самый простой способ

- **VPS:** после публикации репозитория и первого `server-vX.Y.Z` выпуска — одна команда ниже. Нужны Linux amd64/arm64, Docker Engine с Compose 2.24+, Bash 4+, curl, Python 3.8+, sha256sum и openssl; домен и открытые порты описаны ниже.

```bash
script=$(mktemp) && curl --fail --show-error --silent --location --proto '=https' --proto-redir '=https' 'https://raw.githubusercontent.com/nndimka-ops/unyri/HEAD/scripts/selfhost/get.sh' -o "$script" && sudo bash "$script" --repo 'nndimka-ops/unyri'
```

Команда сохраняет загрузчик в файл; его можно просмотреть перед `sudo bash`. Доверяйте только репозиторию владельца. Загрузчик скачивает последний стабильный серверный выпуск (среди 100 последних GitHub releases), проверяет SHA256 архива и всех файлов, распаковывает в `/opt/unyri` и запускает установку с вопросами. При несовпадении хеша установка не запускается, существующая папка не меняется. Контрольная сумма из того же GitHub release защищает от повреждения загрузки, но не заменяет доверие издателю. Для выбранного выпуска добавьте `--version server-vX.Y.Z`. До публикации репозитория, общедоступных GHCR-образов и первого выпуска команда недоступна.

- **Домашний ПК:** мастер в настольном приложении администратора — **скоро**, отдельная работа. Он должен позволить установку без терминала; сейчас доступны ручные шаги Windows/Linux ниже.
- **Ручной способ:** скачайте `unyri-selfhost-X.Y.Z.zip` (Windows) или `.tar.gz` (Linux) и `SHA256SUMS` из GitHub release `server-vX.Y.Z`; проверьте SHA256 архива (`Get-FileHash` / `sha256sum`), распакуйте и следуйте инструкции ниже. Готовые образы скачиваются, компиляция не нужна. Повторный запуск обновляет до версии этого комплекта и показывает образ/ID до и после. Для перехода на другой выпуск сначала сделайте резервную копию, затем замените файлы комплектом нужной версии, сохраняя `.env`.

[English version](SELF_HOSTING_EN.md). Руководство и установщики SH-1 подготовлены для проверки владельцем; установка с нуля и работа телефонов ещё требуют проверки по разделам 7–11 ниже. Все команды ниже выполняйте **на своей новой установке**, из папки выбранного выпуска. Существующий сервер разработчика они не обслуживают.

Свой сервер — это постоянно включённый компьютер, который принимает подключения ваших телефонов. Вы управляете аккаунтами, местом и обновлениями. Телефоны одной установки общаются внутри неё: федерации между серверами нет. Одинаковый ник на другом сервере не переносит аккаунт, историю или ключи. Подключайтесь к оператору, которому доверяете: HTTPS подтверждает адрес, но не надёжность владельца.

## 1. Что приготовить

Лид измерил на этом ПК 17 Nov 2026 в покое: Caddy 16 МБ, backend 25 МБ, Postgres 74 МБ, Redis 5 МБ, MinIO 199 МБ, Coturn 13 МБ — около **330 МБ RAM** суммарно; образы занимали около **1,2 ГБ диска**. Это один проверенный стек; LiveKit в этих цифрах не учтён. Это не предел для пользователей/вложений: оставьте запас ОС, пиков, обновлений, базы, файлов и копий. Рекомендации ниже включают такой запас; для готовых образов Rust/Go не нужны. Сторонние компоненты хранилища: [лицензии и исходные теги](../scripts/selfhost/THIRD_PARTY_NOTICES.md).

- Windows 10/11 с поддержкой WSL 2 и Docker Desktop либо 64-битный Linux/VPS с Docker Engine. Для первой проверки ориентируйтесь на 4 ГБ RAM для работы, лучше 8 ГБ для сборки и не менее 20 ГБ свободного места **сверх** планируемых вложений и резервных копий. Это запас для начала, а не измеренная гарантия вместимости. Сборка Rust/Go может потребовать больше места и времени.
- Компьютер без сна/гибернации на время работы сервера; стабильный интернет. Звонки расходуют исходящий трафик. При выключенном ПК сервер недоступен. На Windows после перезагрузки Docker Desktop должен запуститься; проверьте восстановление без открытой консоли.
- Публичный IPv4, домен или имя DDNS и доступ к роутеру, если ПК дома. На VPS вместо роутера обычно есть облачный firewall/security group.
- Два телефона и два тестовых аккаунта. Для внешней проверки хотя бы один телефон должен быть на мобильном интернете.
- Отдельный диск или защищённое место для резервной копии. Docker-том на том же диске не является резервной копией.

Скачайте проверенный комплект конкретного выпуска, распакуйте, например в `D:\UNYRI` или `/opt/unyri`. Не копируйте папку работающего разработчика, его `.env`, ключи, базу или файлы пользователей. В комплекте есть `docker-compose.selfhost.yml`, `SELFHOST_VERSION`, `SHA256SUMS`, `scripts/selfhost/` и руководства. Compose содержит точные теги этого выпуска для `ghcr.io/nndimka-ops/unyri-server:X.Y.Z`, `unyri-minio:X.Y.Z` и `unyri-mc:X.Y.Z`. Внешний интернет нужен для скачивания образов и сертификата.

Переменная `UNYRI_SERVER_IMAGE` в окружении или собственной `.env` позволяет явно выбрать другой образ сервера; `UNYRI_MINIO_IMAGE` и `UNYRI_MC_IMAGE` — образы хранилища. Если задано переопределение, повторный запуск сохраняет этот выбор; удалите его для возврата к версии комплекта. `latest` установщики по умолчанию не используют. Для разработчиков: полный исходный checkout с `server/` и `shared/`, `bash scripts/selfhost/install.sh --from-source` или `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\install.ps1 -FromSource` (псевдоним `-from-source`). Параметр `--from-source` также поддерживается в PowerShell. Этот режим собирает Rust/Go, требует больше ресурсов и недоступен в компактном комплекте. При следующем обновлении из исходников снова передайте этот флаг. Файл `.selfhost-from-source` сохраняет режим для backup/restore; обычный запуск установщика возвращает готовые образы.

`docker-compose.selfhost.yml` — самостоятельный комплект; не добавляйте к нему `docker-compose.production.yml`, `docker-compose.https.yml` или обычный `docker-compose.yml`. Его постоянное имя проекта — `unyri-selfhost`. На одном Docker Engine допускается одна такая установка с этими портами и именами томов. Для второй используйте отдельную VM/машину.

## 2. Сначала проверьте интернет и имя

### Домашний адрес и CGNAT

1. В Windows откройте PowerShell и выполните `ipconfig`. Найдите IPv4 активного Wi-Fi/Ethernet и «Основной шлюз». Первый адрес принадлежит ПК в домашней сети, второй — роутеру. В Linux используйте `ip -4 address` и `ip -4 route` (строка `default via`).
2. Откройте адрес шлюза в браузере. Частые примеры: `192.168.0.1`, `192.168.1.1`, `192.168.8.1`; используйте именно результат своей команды. Логин/пароль панели могут быть на наклейке или в документах провайдера. Это не обязательно пароль Wi-Fi. Если доступ не получается, спросите владельца роутера/провайдера; не сбрасывайте чужой роутер.
3. В Status / Internet / WAN посмотрите **WAN IPv4**. На том же домашнем интернете откройте сайт провайдера или сервис «мой IP» и сравните публичный IPv4. Сервис узнает ваш IP; установщик обращается к `https://api.ipify.org` только после отдельного согласия.
4. Диапазон `100.64.0.0/10` — это `100.64.0.0–100.127.255.255`, общий адрес провайдера (CGNAT). WAN из `10.*`, `172.16.*–172.31.*`, `192.168.*` тоже не публичный. Если WAN и публичный IPv4 различаются, возможно CGNAT или второй роутер перед вашим. При двойном NAT надо настроить оба роутера; при CGNAT домашнего проброса недостаточно.

У мобильных роутеров CGNAT встречается очень часто — **проверить у провайдера**. Решения: заказать публичный IPv4, поставить сервер на VPS или использовать туннель с публичным входом. Туннель должен переносить не только HTTPS, но и нужные TCP/UDP-медиапорты; обычная HTTP-ссылка звонки не обеспечивает. Туннель в этот установщик не входит.

### Постоянное имя при динамическом IPv4

Постоянное имя дешевле и проще постоянного IP. Создайте A-запись домена на публичный IPv4. Если IPv6 ещё не настроен, удалите неправильную AAAA-запись, иначе часть телефонов и проверка сертификата могут идти не туда. Используйте DNS без HTTP/CDN-прокси для начальной проверки.

Варианты DDNS:

- Router → DDNS / Dynamic DNS: выберите поддерживаемого провайдера и включите обновление имени на самом роутере.
- Бесплатный [DuckDNS и официальный updater](https://www.duckdns.org/install.jsp): создайте имя, выберите `windows-powershell`/`windows-gui` для Windows или `linux-cron` для Linux и выполните инструкции сервиса. Для Windows настройте Планировщик заданий, для Linux — cron согласно странице сервиса. Токен вводите локально в защищённый файл updater, не в чат, Git или общую папку. Проверьте A-запись после смены адреса (`Resolve-DnsName ИМЯ -Type A` или `getent ahostsv4 ИМЯ`). Сторонний updater здесь автоматически не устанавливается.
- Бесплатный поддомен от UNYRI — **план, решение владельца**, действующей услуги и регистрации имён пока нет.

**DDNS обновляет DNS, но не конфигурацию медиасервера.** После изменения публичного IPv4 откройте свой `.env` локальным редактором, измените только `TURN_EXTERNAL_IP`, сохраните и повторите установщик. Он пересоздаст Coturn и, если включён, LiveKit. Старые звонки могут оборваться. Полной автоматизации этого шага в SH-1 нет.

## 3. Какие порты открыть

Таблица точно соответствует новому `docker-compose.selfhost.yml`, `start-turn.sh`, `Caddyfile` и конфигурации LiveKit. Внешний номер должен совпадать с внутренним. Пробрасывайте на **LAN IPv4 ПК**, а не на адрес контейнера/WSL.

| Порт | Протокол | Для чего | Если закрыт |
|---|---|---|---|
| 80 | TCP | HTTP → HTTPS; проверка/обновление сертификата Let's Encrypt | HTTP не перенаправится; один из способов выдачи сертификата недоступен |
| 443 | TCP | HTTPS API, WebSocket `/ws`, админка, подписанные ссылки файлов, сигнализация комнат `/rtc` | Телефоны не подключатся |
| 3478 | UDP | STUN и TURN для личных звонков | Части сетей не удастся установить медиасвязь |
| 3478 | TCP | Альтернативное подключение клиента к TURN | Нет этого запасного пути; выходной relay всё равно UDP |
| 49152–49200 | UDP | Медиапакеты через relay Coturn | Звонок может соединяться без звука/видео или срываться |
| 17881 | TCP | LiveKit ICE TCP, **только с комнатами** | Недоступен TCP-путь медиа комнат |
| 17882 | UDP | LiveKit UDP mux, **только с комнатами** | Недоступен основной UDP-путь медиа комнат |

443/UDP (HTTP/3), 5349 (TURN TLS/DTLS) и диапазон LiveKit 50000–60000 в этой конфигурации **не используются**. Сертификат Caddy не включает `turns:` автоматически. Режим сети, где разрешён только 443/TCP, может требовать другой TURN/TLS-инфраструктуры.

**Не открывайте** 5432/Postgres, 6379/Redis, 9000/MinIO API, 9001/MinIO console, 8080/backend, 7880/LiveKit API и локальный 8081/Caddy health. У них нет host-публикации в этом комплекте. Файлы идут через 443 и путь `/messenger-attachments/...`; отдельный файловый домен не нужен.

Перед скачиванием образов и запуском установщик проверяет TCP 80, 443, 3478 и UDP 3478, 49152–49200; с комнатами также TCP 17881 и UDP 17882. Занятые порты группируются по программе: например, `3478 TCP, 3478 UDP, 49152-49200 UDP: Docker container messenger-coturn`; соседние номера одного протокола объединяются в диапазон, разные владельцы остаются в отдельных строках, затем установка прекращается с кодом 1 до скачивания/запуска. Собственные опубликованные порты проекта Docker `unyri-selfhost` разрешены при повторном запуске; имя `com.docker.backend`/`wslrelay` само по себе не означает «наш». Проверку сокетов запускайте на Docker-хосте: из контейнера видны только его сокеты, но опубликованные порты других Docker-контейнеров всё равно проверяются через Docker. Linux использует `ss` (пакет iproute2), без него — `/proc/net` с неизвестным именем программы. Изменения сокетов после проверки всё ещё могут привести к ошибке запуска.

### Windows Firewall

Установщик работает без прав администратора. Он сначала показывает точные правила ниже и запрашивает повышение прав один раз только для `scripts/selfhost/firewall.ps1`; если отклонить запрос, установка продолжается и печатает эти же команды для ручного запуска. Помощник добавляет правила, если ещё нет правила с таким именем. Ручной вариант — PowerShell **от имени администратора**:

```powershell
New-NetFirewallRule -Name UNYRI-Selfhost-Web -DisplayName UNYRI-Selfhost-Web -Direction Inbound -Action Allow -Protocol TCP -LocalPort 80,443 -Profile Any
New-NetFirewallRule -Name UNYRI-Selfhost-TURN-TCP -DisplayName UNYRI-Selfhost-TURN-TCP -Direction Inbound -Action Allow -Protocol TCP -LocalPort 3478 -Profile Any
New-NetFirewallRule -Name UNYRI-Selfhost-TURN-UDP -DisplayName UNYRI-Selfhost-TURN-UDP -Direction Inbound -Action Allow -Protocol UDP -LocalPort 3478 -Profile Any
New-NetFirewallRule -Name UNYRI-Selfhost-TURN-Relay -DisplayName UNYRI-Selfhost-TURN-Relay -Direction Inbound -Action Allow -Protocol UDP -LocalPort 49152-49200 -Profile Any
# Only if you enable rooms:
New-NetFirewallRule -Name UNYRI-Selfhost-Rooms-TCP -DisplayName UNYRI-Selfhost-Rooms-TCP -Direction Inbound -Action Allow -Protocol TCP -LocalPort 17881 -Profile Any
New-NetFirewallRule -Name UNYRI-Selfhost-Rooms-UDP -DisplayName UNYRI-Selfhost-Rooms-UDP -Direction Inbound -Action Allow -Protocol UDP -LocalPort 17882 -Profile Any
```

Проверьте существующие одноимённые правила, если их меняли вручную: установщик не перезаписывает их. Сторонний антивирус/firewall и правила WSL/Docker Desktop тоже могут блокировать вход.

### Linux: ufw и облачный firewall

Если используете ufw, выполните на своём сервере:

```sh
# Before enabling ufw on a VPS, allow YOUR actual SSH port. Example for port 22:
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 3478/tcp
sudo ufw allow 3478/udp
sudo ufw allow 49152:49200/udp
# Only with rooms:
sudo ufw allow 17881/tcp
sudo ufw allow 17882/udp
sudo ufw status verbose
```

Если ufw выключен, включайте `sudo ufw enable` только после разрешения реального SSH-порта и проверки доступа через консоль VPS. Установщик Linux firewall не меняет. В панели VPS разрешите те же порты/протоколы. У Docker [публикуемые порты могут обходить ufw](https://docs.docker.com/engine/network/packet-filtering-firewalls/); защита внутренних служб здесь основана также на отсутствии `ports`, а внешний фильтр — на router/cloud firewall. Не отключайте Docker firewall и не публикуйте базу ради «проверки».

## 4. Роутер: закрепить ПК и пробросить порты

1. Найдите LAN / DHCP / Address reservation / Static lease / Привязка IP к MAC. Закрепите текущий LAN IPv4 за сетевой картой ПК. При переходе с Wi-Fi на кабель адрес/MAC может измениться. Сохраните настройку и снова проверьте `ipconfig`.
2. Откройте Port Forwarding / Виртуальный сервер / NAT / Переадресация портов (иногда в Advanced / Internet / Security).
3. Для каждой строки таблицы задайте внешний порт/диапазон, тот же внутренний порт/диапазон, нужный протокол и LAN IPv4 ПК. Для 3478 создайте TCP и UDP либо одно правило Both. Для relay укажите диапазон 49152–49200 UDP.
4. Не включайте DMZ для всего ПК. Не открывайте управление роутером из интернета. Если роутер сам занимает 80/443 с WAN, настройте его удалённое управление согласно инструкции производителя.
5. Перед согласием установщик перечисляет точные порты UPnP (включая дополнительные порты комнат). UPnP — необязательная автоматическая попытка. Установщик спрашивает согласие отдельно, ничего не устанавливает. Windows использует доступный системный UPnP COM; Linux — `upnpc` из уже установленного miniupnpc. Если механизма нет, этот шаг пропускается. Результат каждого доступного запроса печатается; проверить в роутере всё равно надо. UPnP может быть выключен владельцем, не работать при CGNAT, терять записи после перезагрузки. Для постоянного сервера надёжнее сохранённые ручные правила.

*Место для скриншотов: «ipconfig — активный адаптер и Основной шлюз»; «DHCP reservation»; «правило TCP 443 на LAN IPv4 ПК»; «диапазон relay UDP». Публикуйте примеры с вымышленными адресами без паролей.*

## 5. Установка на Windows

1. Проверьте поддержку WSL 2/виртуализации по [официальной инструкции Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/). При необходимости выполните в повышенном PowerShell `wsl --install`, перезагрузите Windows и закончите настройку WSL. Установщик UNYRI системное ПО сам не устанавливает.
2. Установите Docker Desktop, включите WSL 2 backend и Linux containers. Запустите Docker Desktop. Проверьте в терминале `docker version` и `docker compose version`: нужен Compose **2.24+**. Работайте с локальным Docker Desktop context; установщик отказывается от remote SSH/TCP Docker contexts.
3. Подготовьте DNS и проброс портов. Затем откройте обычный PowerShell, перейдите в папку выпуска и запустите **одну команду**:

```powershell
cd D:\UNYRI
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\install.ps1
```

`Bypass` действует только для этого процесса. Запускайте проверенный локальный файл. Если политика организации запрещает запуск, согласуйте его с администратором.

Если `.env` отсутствует, но остались тома `unyri-selfhost`, установщик завершится с кодом 1 до создания нового файла: верните прежний `.env` из резервной копии, чтобы сохранить данные, либо явно выполните напечатанные команды удаления перечисленных старых томов/контейнеров и повторите установку; автоматически ничего не удаляется.

4. Введите доменное имя без `https://`, затем «Server name shown in the apps [UNYRI]» — отображаемое имя сервера: 1–64 печатных символа без управляющих, по умолчанию UNYRI. Оно сохраняется как `UNYRI_SERVER_NAME` и передаётся backend; серверная часть из согласованной ветки применяет его, пока имя в базе остаётся исходным COCO, и не заменяет уже настроенное имя. Затем выберите ручной ввод публичного WAN/VPS IPv4 или добровольное определение через api.ipify.org: сервис узнает адрес, найденный IPv4 нужно подтвердить; при отказе или ошибке остаётся ручной ввод. Выберите, нужны ли комнаты. Разрешите UPnP только если хотите эту попытку. Секреты создаются криптографическим генератором, сохраняются в `.env` рядом с Compose, не выводятся. ACL файла ограничивается текущим пользователем и SYSTEM; нужна папка NTFS. Не удаляйте `.env` при повторном запуске.
5. Дождитесь скачивания образов и проверки локального `/health`, затем публичного `https://ИМЯ/health`. Установщик напечатает версии до/после, адрес, админ-команду и QR, если на ПК уже есть `qrencode`; иначе останется копируемая ссылка без стороннего QR-сервиса. С образом SH-2 одноразовый код владельца показывается один раз в приватном интерактивном терминале; команда `coco-admin grant-owner USERNAME` остаётся запасным способом после регистрации (раздел 8).

*Место для скриншотов: «Docker Desktop — Engine running и WSL 2»; «вопросы установщика без .env»; «адрес и локальная успешная проверка».*

## 6. Установка на Linux/VPS

1. Установите Docker Engine и Compose plugin по [инструкции для Ubuntu](https://docs.docker.com/engine/install/ubuntu/) или своей системы. Для Ubuntu после добавления официального apt-репозитория Docker команда установки: `sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin`. Понадобятся также `bash`, `curl`, `openssl` (Ubuntu: `sudo apt install curl openssl`). Установщик объяснит отсутствие Docker и завершится; автоматического `curl | sh` нет.
2. Проверьте `docker version`, `docker compose version` (2.24+), настройте доступ своей учётной записи к локальному Engine. Если нужен root, запускайте ниже через `sudo bash`; созданный `.env` будет доступен root. Доступ к Docker даёт широкие права на машине.
3. Настройте домен, router/cloud firewall и выполните:

```sh
cd /opt/unyri
bash scripts/selfhost/install.sh
```

Вопросы и результат те же, что на Windows. Файл `.env` создаётся с правами 600. Для QR можно заранее установить `qrencode`; для добровольной попытки UPnP — miniupnpc. Это не обязательно для установки. Поддерживается Bash 4+; `/bin/sh install.sh` не подходит.

*Место для скриншота: «терминал Linux — адрес сервера и проверка health, без секретов».*

## 7. Сертификат и телефоны

Коды завершения для терминала и будущего настольного мастера: **0** — локальный стек готов и публичная HTTPS-проверка прошла; **1** — ошибка/занятый порт/неудача запуска; **3** — «установлено, не проверено извне», локальный стек здоров, но публичный HTTPS не подтверждён, данные и работающие службы сохранены. Многие домашние роутеры не умеют обращаться к своему публичному адресу (NAT loopback); реальная проверка — телефон с выключенным Wi-Fi на мобильном интернете. При коде 3 не переустанавливайте и не удаляйте тома: проверьте телефон, DNS, сертификат и проброс.

Caddy получает и продлевает сертификат Let's Encrypt автоматически, если имя указывает на этот сервер, снаружи доступны 80/443 TCP и исходящие DNS/HTTPS. Состояние сертификатов сохраняется в `caddy_data`; не удаляйте том при обновлении. Подробности: [Automatic HTTPS](https://caddyserver.com/docs/automatic-https). Подписанный собственным CA сертификат из `Start-CocoHttps.ps1` относится к разработке в LAN; для этой публичной установки он не используется.

Откройте на телефоне **с выключенным Wi-Fi** `https://ИМЯ/health`. Должен быть HTTP 200 и JSON с `status: "ok"`, `database: true`, `redis: true`, без предупреждения сертификата. На домашнем Wi-Fi доступ через своё публичное имя может не работать из-за NAT loopback/hairpin; это ещё не доказывает недоступность извне. В таком случае настройте локальный DNS на тот же домен и LAN IP, сохраняя HTTPS-имя.

В UNYRI на экране входа/добавления аккаунта откройте выбор «Сервер», введите `https://ИМЯ` **без** `/health`, `/api`, `/administration`, query и fragment. Проверьте карточку сервера и зарегистрируйтесь именно там. Android (`ServerEndpoint.kt`) и iOS (`AppConfig.swift`) сохраняют выбранный origin и выводят WebSocket-адрес `/ws` из него; внешний HTTP в обычных сборках не подходит. TLS-ошибка может выглядеть как отказ безопасного соединения/ошибка подключения; **проверить точный текст в текущих сборках**. Не отключайте проверку сертификата.

QR профиля login step 2 содержит свой сервер отдельно и не является приглашением для регистрации. Приглашение комнаты содержит его: старый формат `coco://conference?server=<закодированный HTTPS origin>&room=...#...`; компактный v2 хранит адрес стороннего сервера внутри fragment, а для стандартного сервера — его fingerprint. Приглашение проверяется относительно выбранного сервера и не переносит аккаунт между серверами. Android в этом срезе пишет/читает `coco://c#...`, iOS пишет `unyri://c#...` и читает оба; **проверить совместимость пересылки iOS → Android**. Приглашения комнат создавайте приложением и передавайте только участникам: в них есть доступ и ключ медиа.

### Телефон: приглашение и первый владелец (SH-3, 18 ноября)

В iOS SH-3 откройте выбор сервера на экране входа либо Настройки → Учётная запись → Сервер → «Сканировать приглашение на сервер». QR приглашения содержит `https://SERVER/#server=<encoded-origin>&invite_code=<encoded-code>`: код находится только во fragment, никогда в query. Сначала подтвердите показанный адрес, затем открывается регистрация с приглашением. Если вы уже вошли, добавляется аккаунт: прежний остаётся доступен в Настройках. Поле кода видно только при invite_required=true. Отказ регистрации обновляет устаревшие сведения сервера.

Зарегистрированная схема также принимает `unyri://server/#server=<encoded-origin>&invite_code=<encoded-code>`. Открытие приложения по HTTPS требует associated domains/AASA; для произвольного собственного домена используйте встроенный сканер. Публичные приглашения требуют HTTPS; локальный HTTP допускается только существующей отладочной настройкой. QR установщика с одним адресом открывает сайт для ручного ввода адреса, а не импортирует приглашение. Коды приглашений не публикуйте.

После входа приложение проверяет доступность первичной настройки. На новом сервере рядом с карточкой сервера появляется «Стать владельцем». Введите или отсканируйте 16-символьный код установщика кнопкой «Сканировать код владельца». Регистр, дефисы и пробелы не важны. Ввод хранится без дефисов; группы по четыре показаны отдельно, чтобы курсор не перескакивал. После принятия обновляется роль и открывается существующая защита входа администратора. На сервере с владельцем этого пункта нет, в том числе на текущем QA. Коды стираются при уходе с экрана/в фон и скрываются во время записи; iOS не блокирует пользовательский скриншот.

В разблокированной админке откройте «Регистрация и приглашения»: владелец меняет требование приглашения, владелец и модератор создают и отзывают коды. По умолчанию — одно использование и семь дней; можно выбрать 1–10000 использований и 1–365 дней. Скопировать/отправить код, ссылку и QR можно только сразу после создания. Владелец видит проверки конфигурации. «Свой сервер» содержит краткие шаги и существующую проверку подключения. DNS/HTTPS/API/WebSocket, внешний звонок и доставку push проверяйте отдельно: настройки TURN и один HTTP 200 не доказывают доступность всех портов. Сборка, CI и телефонные проверки SH-3 на Mac ещё обязательны.

## 8. Как сделать себя администратором

1. Зарегистрируйте аккаунт в приложении на **своём** сервере. По умолчанию регистрация открытая.
2. При первом запуске без владельца backend создаёт одноразовый код вида `ABCD-EFGH-JKLM-NPQR`. Установщик или локальная админ-программа должны прочитать его из приватного файла `COCO_SETUP_CODE_FILE`; по умолчанию это `COCO_DATA_DIR/owner-setup-code` (`/app/data/owner-setup-code` в образе Docker). Код также один раз выводится в журнале backend в строке `FIRST OWNER SETUP CODE`. Не пересылайте журнал с этой строкой.
3. В клиенте с поддержкой SH-2 войдите в аккаунт и введите код на экране «Стать владельцем». Сервер атомарно назначит владельца и уничтожит код. Повторное использование, даже после удаления владельца, невозможно. Экран есть в iOS 0.4.21 (описан выше) и в Android SH-3 (в Профиле); для уже установленных старых версий остаётся вариант через CLI.
4. Обновите профиль и настройте факторы защиты администратора в приложении. Откройте веб-консоль из защищённого раздела приложения.

Если образ поддерживает SH-2 и файл `/app/data/owner-setup-code` существует, установщик показывает код один раз в приватном интерактивном терминале: откройте UNYRI на телефоне → войдите на свой сервер → Профиль → «Стать владельцем» (Claim ownership). При перенаправлении вывода код не печатается; он остаётся в приватном томе `backend_data`, а отметка о показе переживает обновления и резервное копирование. Не записывайте терминальную сессию, не публикуйте код и не помещайте его в логи; после получения прав код обслуживает сервер SH-2.

Пока права не получены, повторный запуск печатает команду приватного просмотра кода даже после первого показа: Linux — `docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml exec -T backend cat /app/data/owner-setup-code > /dev/tty`; в PowerShell используйте напечатанный установщиком вариант с проверкой консоли и `[Console]::WriteLine`, не копируйте код в сообщения и не записывайте терминал.

Если кода нет, клиент ещё не поддерживает получение прав или нужен запасной способ: сначала зарегистрируйте ник в приложении на своём сервере. Из папки выпуска выполните, заменив `my_nickname` своим ником без угловых скобок:

```sh
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml exec backend coco-admin grant-owner my_nickname
```

Это полный вариант `docker compose exec backend coco-admin grant-owner <ник>` для нашего отдельного файла. Утилита уже есть в образе вместе с `messenger-server`; Rust на самом ПК для этой команды не нужен. Команда не создаёт аккаунт и выдаст `Account not found`, если вы зарегистрировались на другом сервере или указали другой ник. Она также отзывает старые административные сессии.

Обновите профиль/заново войдите в приложении, откройте администрирование и настройте второй фактор: authenticator/TOTP, резервные коды и бумажный ключ согласно предложенному экраном режиму. По умолчанию политика включает пароль и оба дополнительных фактора; храните бумажный ключ отдельно от ПК. Точный текущий экран первичной настройки **проверить на телефоне**. Адрес веб-консоли — `https://ИМЯ/administration`; вход можно открыть из защищённого раздела приложения через одноразовый handoff. Знание URL не даёт прав. `COCO_ADMIN_KEY` — ключ шифрования факторов сервера, а не пароль входа; он уже создан установщиком, не заменяйте его случайно.

В консоли заполните имя, контакт оператора, лимит файла, места на аккаунт и общего хранилища. В разделе «Свой сервер» владелец в любой момент переключает открытую регистрацию и регистрацию по приглашениям. Владелец и модераторы создают, просматривают и отзывают приглашения; по умолчанию код действует 7 дней и используется один раз. Код и ссылка доступны для копирования/отправки только при создании. Ссылка хранит адрес сервера и код во фрагменте; iOS и Android SH-3 импортируют её после подтверждения адреса. Отозванный, просроченный или использованный код не подходит. При открытой регистрации приглашение не нужно; временное полное закрытие регистрации остаётся отдельной настройкой.

Владелец также видит проверку публичного URL, TURN, комнат, push, доступности bucket, готовности загрузок, свободного места, версии и миграции. Для проверки TURN передайте в **backend** `TURN_EXTERNAL_IP`, `TURN_MIN_PORT=49152`, `TURN_MAX_PORT=49200`, совпадающие с coturn; для адреса используется существующий `PUBLIC_API_ORIGIN`. SH-1 пока передаёт внешний IP только медиасервисам: установщик/compose нужно согласовать при объединении этапов. Проверка не устанавливает соединение с публичным URL/TURN/LiveKit/push и честно показывает `not_probed`: DNS, сертификат и внешние порты проверьте с мобильного интернета. Запрос к bucket только HEAD, до 5 секунд. Оставьте место для ОС, базы, образов, логов и бэкапа: ноль/«без ограничений» не защищает диск. Подробности: API (docs/ADMIN_API_CONTRACT.md in the source repository), админ-консоль (docs/COCO_ADMIN_CONSOLE.md in the source repository), production checklist (docs/DEPLOYMENT_PRODUCTION.md in the source repository).

### Адреса сервера: подготовлена серверная часть (18 Nov, фаза 1a)

Для карточки «Адреса сервера» сервер теперь отдаёт владельцу и администратору внешний HTTPS-адрес, имя и отдельный порт (в том числе **443**), настроенный внешний IP для звонков, найденный домашний IP и порт ПК, порты личных звонков, состояние комнат и тип установки/входа. Карточки iOS/Android/web/desktop появятся отдельным этапом; эта ветка готовит их данные. Модераторы и обычные пользователи эти сведения не получают. `TURN_EXTERNAL_IP` помечен «указан при установке, сейчас не проверен»; это не новое измерение внешнего IP. Самопроверка не подключается к этим адресам.

ПК заново определяет домашний адрес **при каждом управляемом запуске**: установке, повторной установке/обновлении, возврате из резервного копирования и запуске следующей командой из папки выпуска:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\start.ps1
```

```sh
bash scripts/selfhost/start.sh
```

Windows выбирает физический интерфейс маршрута по умолчанию с наименьшей суммой метрик маршрута и интерфейса; Docker/WSL/Hyper-V/VPN не становятся домашним адресом. Linux использует исходный IPv4 из `ip route get` и проверяет физический интерфейс; нужны `iproute2`, GNU coreutils и `flock` из util-linux. При отсутствии подходящей сети, равнозначном выборе или ошибке старый адрес и его время очищаются: сервер показывает неизвестный домашний адрес. Новое значение применяется через Compose `up --no-build`, при необходимости пересоздаётся backend. Не требуется переустановка с новыми секретами.

Установщик атомарно меняет только `UNYRI_LAN_ADDRESS`, `UNYRI_LAN_PORT`, `UNYRI_LAN_DETECTED_AT`, `UNYRI_HOSTING_KIND`, `UNYRI_INGRESS_MODE`, `UNYRI_TUNNEL_PROVIDER`; остальные строки, секреты и права доступа сохраняются. Тип установки по умолчанию `unknown`: укажите в приватной конфигурации `home_pc` для домашнего ПК или `vps` для дата-центра; при `vps` частная сеть дата-центра не выдаётся за домашнюю. Вход по умолчанию `direct`; `tunnel` и провайдеры `tailscale_funnel` / `cloudflare` — только метаданные уже настроенного входа, не установка туннеля.

Для автозапуска ОС используйте эти же команды после готовности сети и Docker, под учётной записью установки. В этой фазе задача Windows/служба Linux автоматически не регистрируется; это нужно настроить локально и проверить после перезагрузки. **Прямой `docker compose up`, `start`, `restart` или автоматический рестарт контейнера сохраняет последнее записанное значение** и не определяет новый адрес ПК. После смены сети запустите управляемую команду. Если загрузка ОС не дошла до неё, сохранённое время не означает свежую проверку. Не используйте найденный IP как небезопасный HTTP-вход: сохраняйте HTTPS-имя сервера и настройте локальный DNS, не отключайте проверку сертификата. Сборка Rust, реальные установщики, DHCP/перезагрузка и Linux-проверки этой ветки ожидают лида.

### Android SH-3: два телефона без терминала

1. На первом телефоне откройте Настройки → Сервер, введите HTTPS-адрес своего сервера и подтвердите. Адрес выбранного сервера всегда есть в карточке. В «Свой сервер» прочитайте короткую инструкцию; «Проверить подключение» вручную проверяет DNS, TLS, публичный API, минимальную версию приложения и показывает состояние уже работающего WebSocket. Непроверенные поля не означают успех.
2. Зарегистрируйтесь и завершите показ ключа восстановления login2. После обычного входа приложение проверит, можно ли получить права владельца. Только при доступности в Профиле рядом с сервером появится «Стать владельцем».
3. Введите одноразовый 16-символьный код установщика четырьмя группами или сканируйте QR, содержащий сам код. Регистр и дефисы не важны. После успеха роль обновится и откроется существующая настройка защиты администратора. При лимите попыток подождите 15 минут и повторите вручную. На сервере с владельцем строки получения прав нет.
4. В Администрировании → Свой сервер включите «Только по приглашению». Никакого дополнительного поля при открытой регистрации нет. Владелец и модераторы создают приглашение (1–10 000 использований, 1–365 дней), видят статус, использованные попытки, срок и автора, отзывают с подтверждением. Регистрация и самопроверка доступны только владельцу.
5. Сразу при создании скопируйте или отправьте код/ссылку либо покажите QR второму телефону: повторно сервер код не отдаёт. Ссылка имеет вид `https://SERVER/#server=<encoded-origin>&invite_code=<encoded-code>`: код после `#`, никогда после `?`. На втором телефоне используйте QR в Настройки → Сервер или существующий сканер Контактов. При открытии ссылки Android без проверенного домена может предложить «Открыть с помощью» либо оставить её в браузере; тогда используйте QR. Перед сменой сервера подтвердите показанный полный адрес; действующий аккаунт другого сервера выйдет из сеанса. Код подставится в регистрацию. Не публикуйте ссылку с действующим кодом.
6. Выключите Wi-Fi на втором телефоне. Проверьте вход, сообщения в обе стороны, звонок и уведомление при закрытом приложении. Владелец открывает Администрирование → Свой сервер → Проверить сервер и читает пояснение каждого поля. `not_probed` означает «проверьте с телефона на мобильном интернете»: сервер проверяет конфигурацию, а не внешний DNS/TLS, TURN UDP/TCP, комнаты или фактическую доставку push. Если провайдер push не настроен, не ожидайте фоновой доставки.

Android SH-3 подготовлен 18 Nov 2026; проверка двух телефонов лидом на QA обязательна. iOS получит эти экраны с новым Mac. Внедрение не меняет уже выпущенные приложения автоматически.

## 9. Звонки, комнаты и уведомления

Для личного звонка Coturn выдаёт relay, а backend — короткоживущие учётные данные. Секрет TURN совпадает у этих двух служб и не выдаётся телефону. Relay изолирован от базы/Redis/MinIO; пересылка в приватные и служебные сети запрещена. Проверяйте звук/видео между **разными внешними сетями**, а не только двумя телефонами на одном Wi-Fi.

LiveKit включается ответом `y` при первой установке (profile `rooms`). Он использует указанный публичный IPv4, 17881/TCP и 17882/UDP; API 7880 остаётся внутри Docker. `room.auto_create=false`, а каждый публичный `/rtc` проходит авторизацию backend. `/twirp/*` наружу закрыт. См. [существующую схему комнат](../scripts/conference/README.md). **Проверить** получение/расшифровку аудио/видео двумя реальными клиентами; HTTP health этого не проверяет. Если комнаты не выбраны, личные сообщения и личные звонки от LiveKit не зависят.

Официальное приложение на новом сервере получает сообщения через открытое соединение. Фоновые уведомления и входящие звонки при спящем/выгруженном приложении **не обещаются**: общего push relay ещё нет. APNs alert/VoIP в сервере уже реализованы, но нужны разрешённые Apple-ключи для bundle/topic/environment установленного iOS-клиента; FCM — service account именно Firebase-проекта Android-клиента. Случайно созданный ключ другого проекта не подойдёт. Официальные ключи операторам не выдаются. Собственные сборки мобильных приложений могут использовать собственные настройки провайдеров, но это вне установки SH-1.

В стеке явно стоит `UNYRI_OFFLINE=true`: отключена только отправка push через провайдеров, а не работа сервера/интернета. Ключей push нет и ничего монтировать не требуется. Даже принятый провайдером HTTP-запрос не доказывает уведомление на экране. Текущие ограничения и модель будущего relay: push-аудит в полном исходном репозитории (`docs/PUSH_SECURITY_AUDIT_20261113.md`). Android Force stop и системные ограничения проверяются отдельно. Не пытайтесь «включить push» открытием ещё одного входящего порта.

## 10. Обновление, резервная копия, перенос

### Обновление

Автообновления по расписанию нет. Перед обновлением сделайте копию, сохраните точную старую папку выпуска и образы. Получите согласованный выпуск сервера/клиентов, замените файлы проверенным комплектом, сохранив `.env`, и повторите `install.ps1`/`install.sh`. На VPS можно повторить команду загрузчика с нужным `--version`. Установщик скачивает образы версии комплекта, показывает образ/ID до и после и выполняет `up --no-build`; секреты и тома сохраняются. Теги выпуска не являются неизменяемыми registry digests: издателю нельзя переназначать опубликованные версии. При локальной сборке снова нужен `--from-source` / `-FromSource`. Возврат старого образа после SQL-миграций допустим только при совместимой схеме; иначе восстановите полную предшествующую копию на отдельной машине. Пароль PostgreSQL на существующем томе не меняется заменой `POSTGRES_PASSWORD` в `.env`.

### Полная холодная копия

Запланируйте короткий перерыв и проверьте свободное место. Выполните:

```powershell
# Windows, from the release directory:
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\backup.ps1
```

```sh
# Linux:
bash scripts/selfhost/backup.sh
```

Сценарий сначала получает маленький helper-образ, затем останавливает **только проект unyri-selfhost**, архивирует шесть томов (Postgres, Redis, MinIO, Caddy data/config и приватный backend_data) и `.env`, проверяет читаемость архивов и запускает стек снова. Папка `selfhost-backups/ДАТА...` с маркером `COMPLETE` считается завершённой копией. При ошибке маркера нет; проверьте возврат сервера в работу. Скопируйте завершённую папку вместе с точным выпуском исходников на другой защищённый диск; ограничьте доступ, она содержит личные данные, сертификаты и секреты. Копия истории на телефоне и серверный бэкап решают разные задачи: сервер не восстанавливает утраченные клиентские ключи расшифровки.

Старые `scripts/Backup-CocoDatabase.ps1`/`Restore-CocoDatabase.ps1` жёстко проверяют контейнер `messenger-postgres` проекта разработчика и для selfhost **не применяются**. Наши сценарии сохраняют весь стек, не только SQL.

`backend_data` хранит приватные файлы SH-2 (код владельца и отметку его показа), монтируется в `/app/data` с владельцем UID 10001 и входит в шестой архив `backend_data.tgz`. Не выводите содержимое файлов или архивов в логи. Удаление `down --volumes` удаляет также этот том; старые копии из пяти томов требуют отдельного плана миграции до восстановления новым сценарием.

### Восстановление или переезд на другой ПК

Используйте **новый Docker Engine без томов `unyri-selfhost_*`**, например отдельную VM. Это защищает существующую установку: restore откажется, если любой целевой том уже есть. Для аварийного восстановления на том же ПК сначала сохраните повреждённые тома и используйте отдельный Engine; restore их не удаляет.

1. Установите Docker, распакуйте **тот же выпуск** исходников. Перенесите завершённую копию, например в `E:\UNYRI-backup` или `/mnt/backup/unyri`. До первого запуска установщика скопируйте из неё `.env` в корень выпуска. Не генерируйте новые секреты.
2. Выполните восстановление, указав реальную папку копии:

```powershell
Copy-Item -LiteralPath E:\UNYRI-backup\.env -Destination .env
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\restore.ps1 -BackupPath E:\UNYRI-backup
```

```sh
install -m 600 /mnt/backup/unyri/.env .env
bash scripts/selfhost/restore.sh /mnt/backup/unyri
```

3. После успешного restore при переезде измените `TURN_EXTERNAL_IP` и DNS A/DDNS на новый публичный IP. Сохраните прежнее доменное имя: origin участвует в разделении клиентских данных. Переезд на другое имя не является автоматическим переносом аккаунтов в клиентах. Если меняете Docker-подсеть из-за конфликта, согласованно измените `UNYRI_SUBNET`, `UNYRI_PROXY_IP`, `UNYRI_SFU_IP` и `CONFERENCE_LIVEKIT_API_URL` (если комнаты включены).
4. Остановите старый сервер перед направлением пользователей на новый. Запустите обычный установщик на новом, проверьте health, вход обоих аккаунтов, старое вложение и новое сообщение/фото/звонок. После проверки копии сначала можно планировать новое обновление. При ошибке сохраните частично восстановленные тома и разберите причину; не сливайте две базы.

### Остановить или удалить

Из папки выпуска:

```sh
# Stop/remove containers and networks, keep data:
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml down
# Permanent deletion of this stack's SIX volumes: ONLY after checking an independent backup:
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml --profile rooms down --volumes
```

`down --volumes` безвозвратно удаляет данные установки; для обновления эта команда не нужна. Затем удалите только эту папку выпуска и её приватный `.env`, если сервер больше не нужен; независимую копию храните по своей политике. На Windows удалите наши правила:

```powershell
Get-NetFirewallRule -Name 'UNYRI-Selfhost-*' -ErrorAction SilentlyContinue | Remove-NetFirewallRule
```

На роутере удалите только созданные для UNYRI ручные/UPnP-правила. В Linux удалите соответствующие разрешения `sudo ufw delete allow 80/tcp` и аналогично для остальных строк таблицы, **если они не нужны другим службам**. Удалите записи DDNS/updater для этой установки и облачные правила. `docker system prune --volumes` для удаления одной установки не используйте.

## 11. Если не работает

Начните с безопасных команд; не публикуйте `.env`, полный `docker compose config` или `docker inspect` с окружением:

```sh
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml ps -a
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml config --quiet
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml logs --tail 80 backend caddy coturn
```

Логи просматривайте локально: перед отправкой уберите токены, адреса пользователей и личные данные. Caddy access-log специально не включён: подписанные S3/room URL не должны уходить в общие журналы. Для списка локальных портов:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\check-ports.ps1 -Domain family.example.org
```

```sh
bash scripts/selfhost/check-ports.sh
```

| Симптом | Что сделать |
|---|---|
| Docker отсутствует/Engine недоступен | Установить вручную/запустить Docker Desktop или Engine; проверить Linux containers и локальный context. Никакие данные удалять не нужно |
| Сборка/скачивание не завершились | Проверить интернет, свободное место, доступ к GitHub/Cargo/Go/registry. Повторить установщик; не стирать `.env`/тома |
| Address already in use | Порт занят другой службой. Найти её через check-ports; не останавливать неизвестную службу автоматически |
| Pool overlaps with other one | Docker-подсеть конфликтует. Выбрать свободную и согласованно изменить четыре настройки из раздела переезда |
| Локально работает, с мобильного нет | Сравнить WAN/публичный IPv4, A/AAAA, проброс, firewall ПК/облака, CGNAT. TCP-проверка не доказывает UDP |
| С мобильного работает, дома через домен нет | Проверить NAT loopback/локальный DNS. Не менять домен на HTTP/LAN IP в аккаунте |
| Ошибка сертификата | Проверить домен, часы ПК/телефона, DNS, входящие 80/443 и Caddy logs. Не обходить TLS. После исправления дать Caddy повторить выдачу; не удалять том сертификатов ради попытки |
| Установщик сообщил local ready, но public health failed | Стек оставлен работать; исправить DNS/TLS/маршрут. Проверить с мобильного: LAN hairpin может мешать только проверке с ПК |
| Health зелёный, фото/файл не отправляется | Проверить storage-init (Exited 0 ожидаемо), приватный bucket, write-only principal, Caddy S3 path/Host и квоты. Версионирование bucket никогда не включать: даже Suspended не поддерживается |
| Звонок идёт без звука/не соединяется | Проверить 3478 UDP/TCP, весь relay UDP, актуальность TURN_EXTERNAL_IP и DDNS. Проверить в двух внешних сетях; закрытый UDP требует иной TURN/TLS-схемы |
| Комнаты не работают | Проверить `COMPOSE_PROFILES=rooms`, все четыре CONFERENCE-настройки, текущий публичный IP, 17881/TCP+17882/UDP и gateway. Не публиковать 7880/Twirp |
| Нет push при закрытом приложении | Это ожидаемое ограничение официальных клиентов до push relay; дополнительные входящие порты его не исправят |
| Админ-команда не находит аккаунт/не даёт вход | Сверить ник и выбранный в приложении сервер; обновить профиль, пройти факторы. Восстановить исходный COCO_ADMIN_KEY из своей копии, не генерировать замену |
| Нет места | Освободить место вне данных установки, ограничить квоты/сделать бэкап. Не удалять Docker-тома, чтобы «почистить кэш» |

Для проверки TCP **с другого интернета**: `Test-NetConnection family.example.org -Port 443`, затем 3478 и при комнатах 17881. 80 можно проверить HTTP-redirect. UDP проверяйте реальным TURN-звонком/авторизованным TURN-тестером: проверка TCP или сайт «порт открыт» недостаточны. Запишите выпуск, ОС, время, симптом и этап; пункты, оставленные как «проверить», перечислены в отчёте SH-1.
