# Власний сервер UNYRI: Windows, домашній ПК або VPS

## Ви — оператор свого сервера

Встановивши сервер, ви стаєте його оператором: ви відповідаєте за сервер, його користувачів та їхні дані, оновлення й резервні копії, правила, розгляд скарг і дотримання закону там, де працює сервер (наприклад, за політику конфіденційності для ваших користувачів). Розробник UNYRI не керує вашим сервером, не має до нього доступу й не відповідає за нього. Програма надається «як є», без гарантій (AGPL-3.0).

## Найпростіший спосіб

- **VPS:** після публікації репозиторію та першого випуску `server-vX.Y.Z` — одна команда нижче. Потрібні Linux amd64/arm64, Docker Engine із Compose 2.24+, Bash 4+, curl, Python 3.8+, sha256sum та openssl; домен і відкриті порти описано нижче.

```bash
script=$(mktemp) && curl --fail --show-error --silent --location --proto '=https' --proto-redir '=https' 'https://raw.githubusercontent.com/nndimka-ops/unyri/HEAD/scripts/selfhost/get.sh' -o "$script" && sudo bash "$script" --repo 'nndimka-ops/unyri'
```

Команда зберігає завантажувач у файл; його можна переглянути перед `sudo bash`. Довіряйте лише репозиторію власника. Завантажувач отримує найновіший стабільний випуск сервера (серед 100 останніх випусків GitHub), перевіряє SHA256 архіву та всіх файлів, розпаковує в `/opt/unyri` і запускає встановлення із запитаннями. Якщо хеш не збігається, встановлення не починається, наявна папка не змінюється. Контрольна сума з того самого випуску GitHub захищає від пошкодження під час завантаження, але не замінює довіри до видавця. Щоб вибрати певний випуск, додайте `--version server-vX.Y.Z`. До публікації репозиторію, загальнодоступних образів GHCR і першого випуску команда недоступна.

- **Домашній ПК:** майстер у настільному застосунку адміністратора — **незабаром**, це окреме завдання. Він має дати змогу встановити сервер без термінала; зараз доступні наведені нижче ручні кроки для Windows/Linux.
- **Ручний спосіб:** завантажте `unyri-selfhost-X.Y.Z.zip` (Windows) або `.tar.gz` (Linux) і `SHA256SUMS` із випуску GitHub `server-vX.Y.Z`; перевірте SHA256 архіву (`Get-FileHash` / `sha256sum`), розпакуйте та дотримуйтеся інструкції нижче. Готові образи завантажуються, компіляція не потрібна. Повторний запуск оновлює до версії цього комплекту й показує образ/ID до та після оновлення. Щоб перейти на інший випуск, спочатку створіть резервну копію, а потім замініть файли комплектом потрібної версії, зберігши `.env`.

[Англійська версія](SELF_HOSTING_EN.md). Посібник та інсталятори SH-1 підготовлено для перевірки власником; встановлення з нуля й роботу телефонів ще потрібно перевірити за розділами 7–11 нижче. Усі наведені нижче команди виконуйте **на власній новій інсталяції**, з папки вибраного випуску. Наявний сервер розробника вони не обслуговують.

Власний сервер — це постійно ввімкнений комп’ютер, який приймає підключення ваших телефонів. Ви керуєте обліковими записами, місцем у сховищі й оновленнями. Телефони однієї інсталяції спілкуються в її межах: федерації між серверами немає. Однаковий нік на іншому сервері не переносить обліковий запис, історію чи ключі. Підключайтеся до оператора, якому довіряєте: HTTPS підтверджує адресу, але не надійність власника.

## 1. Що підготувати

Керівник команди виміряв на цьому ПК 17 листопада 2026 року в стані спокою: Caddy 16 МБ, backend 25 МБ, Postgres 74 МБ, Redis 5 МБ, MinIO 199 МБ, Coturn 13 МБ — загалом близько **330 МБ RAM**; образи займали близько **1,2 ГБ на диску**. Це один перевірений набір компонентів; LiveKit у цих цифрах не враховано. Це не межа кількості користувачів/вкладень: залиште запас для ОС, пікових навантажень, оновлень, бази, файлів і копій. Наведені нижче рекомендації враховують такий запас; для готових образів Rust/Go не потрібні. Сторонні компоненти сховища: [ліцензії та теги вихідного коду](../scripts/selfhost/THIRD_PARTY_NOTICES.md).

- Windows 10/11 із підтримкою WSL 2 та Docker Desktop або 64-бітний Linux/VPS із Docker Engine. Для першої перевірки орієнтуйтеся на 4 ГБ RAM для роботи, краще 8 ГБ для збирання та щонайменше 20 ГБ вільного місця **додатково до** запланованих вкладень і резервних копій. Це початковий запас, а не виміряна гарантія місткості. Збирання Rust/Go може потребувати більше місця й часу.
- Комп’ютер без переходу в режим сну/гібернації під час роботи сервера; стабільний інтернет. Дзвінки витрачають вихідний трафік. Коли ПК вимкнений, сервер недоступний. У Windows після перезавантаження має запуститися Docker Desktop; перевірте відновлення роботи без відкритої консолі.
- Публічна IPv4-адреса, домен або ім’я DDNS і доступ до роутера, якщо ПК удома. На VPS замість роутера зазвичай є хмарний firewall/security group.
- Два телефони та два тестові облікові записи. Для зовнішньої перевірки хоча б один телефон має користуватися мобільним інтернетом.
- Окремий диск або захищене місце для резервної копії. Том Docker на тому самому диску не є резервною копією.

Завантажте перевірений комплект конкретного випуску й розпакуйте, наприклад у `D:\UNYRI` або `/opt/unyri`. Не копіюйте робочу папку розробника, його `.env`, ключі, базу чи файли користувачів. У комплекті є `docker-compose.selfhost.yml`, `SELFHOST_VERSION`, `SHA256SUMS`, `scripts/selfhost/` і посібники. Compose містить точні теги цього випуску для `ghcr.io/nndimka-ops/unyri-server:X.Y.Z`, `unyri-minio:X.Y.Z` і `unyri-mc:X.Y.Z`. Зовнішній доступ до інтернету потрібен для завантаження образів і отримання сертифіката.

Змінна `UNYRI_SERVER_IMAGE` у середовищі або власному `.env` дає змогу явно вибрати інший образ сервера; `UNYRI_MINIO_IMAGE` та `UNYRI_MC_IMAGE` — образи сховища. Якщо задано інше значення, повторний запуск зберігає цей вибір; видаліть його, щоб повернутися до версії комплекту. Інсталятори типово не використовують `latest`. Для розробників: повна робоча копія вихідного коду з `server/` і `shared/`, `bash scripts/selfhost/install.sh --from-source` або `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\install.ps1 -FromSource` (псевдонім `-from-source`). Параметр `--from-source` також підтримується в PowerShell. Цей режим збирає Rust/Go, потребує більше ресурсів і недоступний у компактному комплекті. Під час наступного оновлення з вихідного коду знову передайте цей прапорець. Файл `.selfhost-from-source` зберігає режим для резервного копіювання/відновлення; звичайний запуск інсталятора повертає готові образи.

`docker-compose.selfhost.yml` — самостійний комплект; не додавайте до нього `docker-compose.production.yml`, `docker-compose.https.yml` або звичайний `docker-compose.yml`. Його постійне ім’я проєкту — `unyri-selfhost`. На одному Docker Engine допускається одна така інсталяція із цими портами та іменами томів. Для другої використовуйте окрему VM/машину.

## 2. Спочатку перевірте інтернет та ім’я

### Домашня адреса й CGNAT

1. У Windows відкрийте PowerShell і виконайте `ipconfig`. Знайдіть IPv4 активного Wi-Fi/Ethernet та «Основний шлюз». Перша адреса належить ПК у домашній мережі, друга — роутеру. У Linux використовуйте `ip -4 address` та `ip -4 route` (рядок `default via`).
2. Відкрийте адресу шлюзу в браузері. Поширені приклади: `192.168.0.1`, `192.168.1.1`, `192.168.8.1`; використовуйте саме результат своєї команди. Логін/пароль панелі можуть бути на наліпці або в документах провайдера. Це не обов’язково пароль Wi-Fi. Якщо не вдається отримати доступ, зверніться до власника роутера/провайдера; не скидайте налаштування чужого роутера.
3. У Status / Internet / WAN подивіться **WAN IPv4**. Через те саме домашнє підключення до інтернету відкрийте сайт провайдера або сервіс «моя IP-адреса» та порівняйте публічну IPv4-адресу. Сервіс дізнається вашу IP-адресу; інсталятор звертається до `https://api.ipify.org` лише після окремої згоди.
4. Діапазон `100.64.0.0/10` — це `100.64.0.0–100.127.255.255`, спільні адреси провайдера (CGNAT). WAN-адреси з `10.*`, `172.16.*–172.31.*`, `192.168.*` теж не публічні. Якщо WAN і публічна IPv4-адреса відрізняються, можливо, у вас CGNAT або перед вашим роутером є другий. За подвійного NAT потрібно налаштувати обидва роутери; за CGNAT домашнього перенаправлення портів недостатньо.

У мобільних роутерів CGNAT трапляється дуже часто — **перевірте в провайдера**. Рішення: замовити публічну IPv4-адресу, встановити сервер на VPS або використати тунель із публічною точкою входу. Тунель має передавати не лише HTTPS, а й потрібний трафік TCP/UDP через медіапорти; звичайне HTTP-посилання не забезпечує дзвінків. Тунель до цього інсталятора не входить.

### Постійне ім’я за динамічної IPv4-адреси

Постійне ім’я дешевше й простіше за постійну IP-адресу. Створіть A-запис домену, що вказує на публічну IPv4-адресу. Якщо IPv6 ще не налаштовано, видаліть неправильний AAAA-запис, інакше частина телефонів і перевірка сертифіката можуть звертатися не за тією адресою. Для початкової перевірки використовуйте DNS без HTTP/CDN-проксі.

Варіанти DDNS:

- Router → DDNS / Dynamic DNS: виберіть підтримуваного провайдера та ввімкніть оновлення імені на самому роутері.
- Безплатний [DuckDNS та офіційна програма оновлення](https://www.duckdns.org/install.jsp): створіть ім’я, виберіть `windows-powershell`/`windows-gui` для Windows або `linux-cron` для Linux і виконайте інструкції сервісу. Для Windows налаштуйте Планувальник завдань, для Linux — cron згідно зі сторінкою сервісу. Токен вводьте локально в захищений файл програми оновлення, а не в чат, Git чи спільну папку. Перевірте A-запис після зміни адреси (`Resolve-DnsName ИМЯ -Type A` або `getent ahostsv4 ИМЯ`). Стороння програма оновлення тут автоматично не встановлюється.
- Безплатний піддомен від UNYRI — **план, рішення за власником**; чинної послуги та реєстрації імен поки немає.

**DDNS оновлює DNS, але не конфігурацію медіасервера.** Після зміни публічної IPv4-адреси відкрийте свій `.env` у локальному редакторі, змініть лише `TURN_EXTERNAL_IP`, збережіть і повторно запустіть інсталятор. Він заново створить Coturn і, якщо ввімкнено, LiveKit. Поточні дзвінки можуть обірватися. Повної автоматизації цього кроку в SH-1 немає.

## 3. Які порти відкрити

Таблиця точно відповідає новому `docker-compose.selfhost.yml`, `start-turn.sh`, `Caddyfile` і конфігурації LiveKit. Зовнішній номер має збігатися з внутрішнім. Перенаправляйте порти на **LAN IPv4 ПК**, а не на адресу контейнера/WSL.

| Порт | Протокол | Призначення | Якщо закритий |
|---|---|---|---|
| 80 | TCP | HTTP → HTTPS; перевірка/оновлення сертифіката Let's Encrypt | HTTP не перенаправлятиметься; один зі способів видачі сертифіката недоступний |
| 443 | TCP | HTTPS API, WebSocket `/ws`, панель адміністратора, підписані посилання на файли, сигналізація кімнат `/rtc` | Телефони не підключаться |
| 3478 | UDP | STUN і TURN для особистих дзвінків | У деяких мережах не вдасться встановити медіазв’язок |
| 3478 | TCP | Альтернативне підключення клієнта до TURN | Цей запасний шлях недоступний; вихідний трафік ретранслятора все одно використовує UDP |
| 49152–49200 | UDP | Медіапакети через ретранслятор Coturn | Дзвінок може встановлюватися без звуку/відео або обриватися |
| 17881 | TCP | LiveKit ICE TCP, **лише з кімнатами** | TCP-шлях передавання медіа кімнат недоступний |
| 17882 | UDP | LiveKit UDP mux, **лише з кімнатами** | Основний UDP-шлях передавання медіа кімнат недоступний |

443/UDP (HTTP/3), 5349 (TURN TLS/DTLS) і діапазон LiveKit 50000–60000 у цій конфігурації **не використовуються**. Сертифікат Caddy не вмикає `turns:` автоматично. Режим мережі, де дозволено лише 443/TCP, може потребувати іншої інфраструктури TURN/TLS.

**Не відкривайте** 5432/Postgres, 6379/Redis, 9000/MinIO API, 9001/MinIO console, 8080/backend, 7880/LiveKit API та локальний 8081/Caddy health. У цьому комплекті ці порти не опубліковано на хості. Файли передаються через 443 і шлях `/messenger-attachments/...`; окремий домен для файлів не потрібен.

Перед завантаженням образів і запуском інсталятор перевіряє TCP 80, 443, 3478 та UDP 3478, 49152–49200; з кімнатами також TCP 17881 та UDP 17882. Зайняті порти групуються за програмою: наприклад, `3478 TCP, 3478 UDP, 49152-49200 UDP: Docker container messenger-coturn`; сусідні номери одного протоколу об’єднуються в діапазон, різні власники залишаються в окремих рядках, після чого встановлення припиняється з кодом 1 до завантаження/запуску. Власні опубліковані порти проєкту Docker `unyri-selfhost` дозволені під час повторного запуску; сама назва `com.docker.backend`/`wslrelay` не означає «наш». Перевірку сокетів запускайте на хості Docker: із контейнера видно лише його сокети, але опубліковані порти інших контейнерів Docker усе одно перевіряються через Docker. Linux використовує `ss` (пакет iproute2), а без нього — `/proc/net` із невідомою назвою програми. Зміни сокетів після перевірки все ще можуть призвести до помилки запуску.

### Windows Firewall

Інсталятор працює без прав адміністратора. Спочатку він показує наведені нижче точні правила й один раз запитує підвищення прав лише для `scripts/selfhost/firewall.ps1`; якщо відхилити запит, встановлення продовжиться й буде виведено ті самі команди для ручного запуску. Допоміжний сценарій додає правила, якщо правила з таким ім’ям ще немає. Ручний варіант — PowerShell **від імені адміністратора**:

```powershell
New-NetFirewallRule -Name UNYRI-Selfhost-Web -DisplayName UNYRI-Selfhost-Web -Direction Inbound -Action Allow -Protocol TCP -LocalPort 80,443 -Profile Any
New-NetFirewallRule -Name UNYRI-Selfhost-TURN-TCP -DisplayName UNYRI-Selfhost-TURN-TCP -Direction Inbound -Action Allow -Protocol TCP -LocalPort 3478 -Profile Any
New-NetFirewallRule -Name UNYRI-Selfhost-TURN-UDP -DisplayName UNYRI-Selfhost-TURN-UDP -Direction Inbound -Action Allow -Protocol UDP -LocalPort 3478 -Profile Any
New-NetFirewallRule -Name UNYRI-Selfhost-TURN-Relay -DisplayName UNYRI-Selfhost-TURN-Relay -Direction Inbound -Action Allow -Protocol UDP -LocalPort 49152-49200 -Profile Any
# Only if you enable rooms:
New-NetFirewallRule -Name UNYRI-Selfhost-Rooms-TCP -DisplayName UNYRI-Selfhost-Rooms-TCP -Direction Inbound -Action Allow -Protocol TCP -LocalPort 17881 -Profile Any
New-NetFirewallRule -Name UNYRI-Selfhost-Rooms-UDP -DisplayName UNYRI-Selfhost-Rooms-UDP -Direction Inbound -Action Allow -Protocol UDP -LocalPort 17882 -Profile Any
```

Перевірте наявні однойменні правила, якщо їх змінювали вручну: інсталятор не перезаписує їх. Сторонній антивірус/брандмауер і правила WSL/Docker Desktop теж можуть блокувати вхідні підключення.

### Linux: ufw та хмарний брандмауер

Якщо використовуєте ufw, виконайте на своєму сервері:

```sh
# Before enabling ufw on a VPS, allow YOUR actual SSH port. Example for port 22:
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 3478/tcp
sudo ufw allow 3478/udp
sudo ufw allow 49152:49200/udp
# Only with rooms:
sudo ufw allow 17881/tcp
sudo ufw allow 17882/udp
sudo ufw status verbose
```

Якщо ufw вимкнено, вмикайте його командою `sudo ufw enable` лише після дозволу справжнього SSH-порту та перевірки доступу через консоль VPS. Інсталятор для Linux не змінює брандмауер. У панелі VPS дозвольте ті самі порти/протоколи. У Docker [опубліковані порти можуть обходити ufw](https://docs.docker.com/engine/network/packet-filtering-firewalls/); захист внутрішніх служб тут також ґрунтується на відсутності `ports`, а зовнішню фільтрацію забезпечує брандмауер роутера/хмарний брандмауер. Не вимикайте брандмауер Docker і не публікуйте базу заради «перевірки».

## 4. Роутер: закріпіть адресу ПК і налаштуйте переадресацію портів

1. Знайдіть LAN / DHCP / Address reservation / Static lease / Прив’язка IP до MAC. Закріпіть поточну LAN IPv4-адресу за мережевою картою ПК. У разі переходу з Wi-Fi на кабель адреса/MAC може змінитися. Збережіть налаштування й знову перевірте `ipconfig`.
2. Відкрийте Port Forwarding / Віртуальний сервер / NAT / Переадресація портів (іноді в Advanced / Internet / Security).
3. Для кожного рядка таблиці задайте зовнішній порт/діапазон, такий самий внутрішній порт/діапазон, потрібний протокол і LAN IPv4 ПК. Для 3478 створіть TCP і UDP або одне правило Both. Для relay вкажіть діапазон 49152–49200 UDP.
4. Не вмикайте DMZ для всього ПК. Не відкривайте керування роутером з інтернету. Якщо сам роутер займає 80/443 з боку WAN, налаштуйте його віддалене керування за інструкцією виробника.
5. Перш ніж запитати згоду, інсталятор перелічує точні порти UPnP (зокрема додаткові порти кімнат). UPnP — необов’язкова спроба автоматичного налаштування. Інсталятор окремо запитує згоду й нічого не встановлює. Windows використовує доступний системний UPnP COM; Linux — `upnpc` з уже встановленого miniupnpc. Якщо механізму немає, цей крок пропускається. Результат кожного доступного запиту виводиться на екран; перевірити його в роутері все одно потрібно. Власник може вимкнути UPnP; він може не працювати за CGNAT і втрачати записи після перезавантаження. Для постійного сервера надійніші збережені правила, налаштовані вручну.

*Місце для знімків екрана: «ipconfig — активний адаптер і Основний шлюз»; «DHCP reservation»; «правило TCP 443 на LAN IPv4 ПК»; «діапазон relay UDP». Публікуйте приклади з вигаданими адресами без паролів.*

## 5. Встановлення на Windows

1. Перевірте підтримку WSL 2/віртуалізації за [офіційною інструкцією Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/). За потреби виконайте в PowerShell з правами адміністратора `wsl --install`, перезавантажте Windows і завершіть налаштування WSL. Інсталятор UNYRI сам не встановлює системне ПЗ.
2. Встановіть Docker Desktop, увімкніть WSL 2 backend і Linux containers. Запустіть Docker Desktop. Перевірте в терміналі `docker version` і `docker compose version`: потрібен Compose **2.24+**. Працюйте з локальним контекстом Docker Desktop; інсталятор відхиляє віддалені контексти Docker через SSH/TCP.
3. Підготуйте DNS і переадресацію портів. Потім відкрийте звичайний PowerShell, перейдіть до папки випуску й запустіть **одну команду**:

```powershell
cd D:\UNYRI
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\install.ps1
```

`Bypass` діє лише для цього процесу. Запускайте перевірений локальний файл. Якщо політика організації забороняє запуск, погодьте його з адміністратором.

Якщо `.env` немає, але залишилися томи `unyri-selfhost`, інсталятор завершиться з кодом 1 до створення нового файлу: поверніть попередній `.env` з резервної копії, щоб зберегти дані, або явно виконайте виведені команди видалення перелічених старих томів/контейнерів і повторіть встановлення; автоматично нічого не видаляється.

4. Введіть доменне ім’я без `https://`, потім «Server name shown in the apps [UNYRI]» — назву сервера, яку буде показано в застосунках: 1–64 друковані символи без керувальних символів, типово UNYRI. Вона зберігається як `UNYRI_SERVER_NAME` і передається backend; серверна частина з узгодженої гілки застосовує її, поки назва в базі залишається початковою COCO, і не замінює вже налаштовану назву. Далі виберіть ручне введення публічної WAN/VPS IPv4 або добровільне визначення через api.ipify.org: сервіс дізнається адресу, а знайдену IPv4 потрібно підтвердити; у разі відмови або помилки залишається ручне введення. Виберіть, чи потрібні кімнати. Дозвольте UPnP, лише якщо хочете спробувати цей спосіб. Секрети створюються криптографічним генератором, зберігаються в `.env` поруч із Compose і не виводяться на екран. ACL файлу обмежується поточним користувачем і SYSTEM; потрібна папка NTFS. Не видаляйте `.env` під час повторного запуску.
5. Дочекайтеся завантаження образів і перевірки локального `/health`, потім публічного `https://ИМЯ/health`. Інсталятор виведе версії до/після, адресу, команду адміністратора та QR, якщо на ПК уже є `qrencode`; інакше залишиться посилання для копіювання без стороннього QR-сервісу. З образом SH-2 одноразовий код власника показується один раз у приватному інтерактивному терміналі; команда `coco-admin grant-owner USERNAME` залишається запасним способом після реєстрації (розділ 8).

*Місце для знімків екрана: «Docker Desktop — Engine running і WSL 2»; «запитання інсталятора без .env»; «адреса й успішна локальна перевірка».*

## 6. Встановлення на Linux/VPS

1. Встановіть Docker Engine і Compose plugin за [інструкцією для Ubuntu](https://docs.docker.com/engine/install/ubuntu/) або своєї системи. Для Ubuntu після додавання офіційного apt-репозиторію Docker команда встановлення: `sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin`. Також знадобляться `bash`, `curl`, `openssl` (Ubuntu: `sudo apt install curl openssl`). Інсталятор повідомить, що Docker відсутній, і завершить роботу; автоматичного `curl | sh` немає.
2. Перевірте `docker version`, `docker compose version` (2.24+), налаштуйте доступ свого облікового запису до локального Engine. Якщо потрібен root, запускайте наведену нижче команду через `sudo bash`; створений `.env` буде доступний root. Доступ до Docker дає широкі права на комп’ютері.
3. Налаштуйте домен, роутер/хмарний брандмауер і виконайте:

```sh
cd /opt/unyri
bash scripts/selfhost/install.sh
```

Запитання й результат такі самі, як на Windows. Файл `.env` створюється з правами 600. Для QR можна заздалегідь встановити `qrencode`; для добровільної спроби UPnP — miniupnpc. Це не обов’язково для встановлення. Підтримується Bash 4+; `/bin/sh install.sh` не підходить.

*Місце для знімка екрана: «термінал Linux — адреса сервера й перевірка health, без секретів».*

## 7. Сертифікат і телефони

Коди завершення для термінала й майбутнього настільного майстра: **0** — локальний стек працює справно, публічна перевірка HTTPS пройшла; **1** — помилка/зайнятий порт/невдалий запуск; **3** — «встановлено, не перевірено ззовні»: локальний стек працює справно, але публічний HTTPS не підтверджено, дані й запущені служби збережено. Багато домашніх роутерів не вміють звертатися до власної публічної адреси (NAT loopback); справжня перевірка — телефон з вимкненим Wi-Fi на мобільному інтернеті. За коду 3 не перевстановлюйте сервер і не видаляйте томи: перевірте телефон, DNS, сертифікат і переадресацію.

Caddy автоматично отримує та поновлює сертифікат Let's Encrypt, якщо ім’я вказує на цей сервер, ззовні доступні 80/443 TCP і працюють вихідні DNS/HTTPS. Стан сертифікатів зберігається в `caddy_data`; не видаляйте том під час оновлення. Докладніше: [Automatic HTTPS](https://caddyserver.com/docs/automatic-https). Сертифікат, підписаний власним CA, зі `Start-CocoHttps.ps1` призначений для розробки в LAN; для цієї публічної інсталяції він не використовується.

Відкрийте на телефоні **з вимкненим Wi-Fi** `https://ИМЯ/health`. Має бути HTTP 200 і JSON зі `status: "ok"`, `database: true`, `redis: true`, без попередження про сертифікат. У домашній мережі Wi-Fi доступ через власне публічне ім’я може не працювати через NAT loopback/hairpin; це ще не доводить недоступності ззовні. У такому разі налаштуйте локальний DNS на той самий домен і LAN IP, зберігаючи HTTPS-ім’я.

В UNYRI на екрані входу/додавання облікового запису відкрийте вибір «Сервер», введіть `https://ИМЯ` **без** `/health`, `/api`, `/administration`, параметрів запиту й фрагмента. Перевірте картку сервера й зареєструйтеся саме на ньому. Android (`ServerEndpoint.kt`) та iOS (`AppConfig.swift`) зберігають вибраний origin і формують на його основі WebSocket-адресу `/ws`; зовнішній HTTP у звичайних збірках не підходить. Помилка TLS може відображатися як відмова в безпечному з’єднанні/помилка підключення; **перевірити точний текст у поточних збірках**. Не вимикайте перевірку сертифіката.

QR профілю login step 2 містить свій сервер окремо й не є запрошенням для реєстрації. Запрошення до кімнати містить його: старий формат `coco://conference?server=<закодированный HTTPS origin>&room=...#...`; компактний v2 зберігає адресу стороннього сервера всередині фрагмента, а для стандартного сервера — його fingerprint. Запрошення перевіряється відносно вибраного сервера й не переносить обліковий запис між серверами. Android у цьому зрізі записує/читає `coco://c#...`, iOS записує `unyri://c#...` і читає обидва; **перевірити сумісність пересилання iOS → Android**. Створюйте запрошення до кімнат у застосунку й передавайте лише учасникам: вони містять дані доступу та ключ медіа.

### Телефон: запрошення та перший власник (SH-3, 18 листопада)

В iOS SH-3 відкрийте вибір сервера на екрані входу або Налаштування → Обліковий запис → Сервер → «Сканувати запрошення на сервер». QR запрошення містить `https://SERVER/#server=<encoded-origin>&invite_code=<encoded-code>`: код розміщено лише у фрагменті, ніколи в параметрах запиту. Спершу підтвердьте показану адресу, після чого відкриється реєстрація із запрошенням. Якщо ви вже ввійшли, додається обліковий запис: попередній залишається доступним у розділі «Налаштування». Поле коду видно лише за invite_required=true. Відмова в реєстрації оновлює застарілі відомості про сервер.

Зареєстрована схема також приймає `unyri://server/#server=<encoded-origin>&invite_code=<encoded-code>`. Відкриття застосунку через HTTPS потребує associated domains/AASA; для довільного власного домену використовуйте вбудований сканер. Публічні запрошення потребують HTTPS; локальний HTTP допускається лише за наявним налагоджувальним налаштуванням. QR інсталятора з однією адресою відкриває сайт для ручного введення адреси, а не імпортує запрошення. Не публікуйте коди запрошень.

Після входу застосунок перевіряє, чи доступне первинне налаштування. На новому сервері поруч із карткою сервера з’являється «Стати власником». Введіть 16-символьний код інсталятора або відскануйте його кнопкою «Сканувати код власника». Регістр, дефіси й пробіли не мають значення. Введений код зберігається без дефісів; групи по чотири символи показано окремо, щоб курсор не перескакував. Після прийняття коду оновлюється роль і відкривається наявний захист входу адміністратора. На сервері з власником цього пункту немає, зокрема на поточному QA. Коди стираються після виходу з екрана/переходу у фон і приховуються під час запису; iOS не блокує знімок екрана, зроблений користувачем.

У розблокованій панелі адміністрування відкрийте «Реєстрація та запрошення»: власник змінює вимогу запрошення, власник і модератор створюють та відкликають коди. Типово — одне використання й сім днів; можна вибрати 1–10000 використань і 1–365 днів. Скопіювати/надіслати код, посилання та QR можна лише відразу після створення. Власник бачить перевірки конфігурації. «Власний сервер» містить короткі кроки й наявну перевірку з’єднання. DNS/HTTPS/API/WebSocket, зовнішній дзвінок і доставку push перевіряйте окремо: налаштування TURN та один HTTP 200 не доводять доступності всіх портів. Для SH-3 іще обов’язкові збирання на Mac, перевірки CI та перевірки на телефонах.

## 8. Як надати собі права адміністратора

1. Зареєструйте обліковий запис у застосунку на **власному** сервері. Типово реєстрація відкрита.
2. Під час першого запуску без власника backend створює одноразовий код на зразок `ABCD-EFGH-JKLM-NPQR`. Інсталятор або локальна програма адміністрування мають прочитати його з приватного файлу `COCO_SETUP_CODE_FILE`; типово це `COCO_DATA_DIR/owner-setup-code` (`/app/data/owner-setup-code` в образі Docker). Код також один раз виводиться в журналі backend у рядку `FIRST OWNER SETUP CODE`. Не пересилайте журнал із цим рядком.
3. У клієнті з підтримкою SH-2 увійдіть в обліковий запис і введіть код на екрані «Стати власником». Сервер атомарно призначить власника й знищить код. Повторне використання неможливе, навіть після видалення власника. Екран є в iOS 0.4.21 (описаний вище) та в Android SH-3 (у розділі «Профіль»); для вже встановлених старих версій залишається варіант через CLI.
4. Оновіть профіль і налаштуйте фактори захисту адміністратора в застосунку. Відкрийте вебконсоль із захищеного розділу застосунку.

Якщо образ підтримує SH-2 і файл `/app/data/owner-setup-code` існує, інсталятор показує код один раз у приватному інтерактивному терміналі: відкрийте UNYRI на телефоні → увійдіть на власний сервер → Профіль → «Стати власником» (Claim ownership). У разі перенаправлення виводу код не друкується; він залишається в приватному томі `backend_data`, а позначка про показ зберігається після оновлень і резервного копіювання. Не записуйте сеанс термінала, не публікуйте код і не додавайте його до журналів; після отримання прав код обробляє сервер SH-2.

Поки права не отримано, повторний запуск виводить команду приватного перегляду коду навіть після першого показу: Linux — `docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml exec -T backend cat /app/data/owner-setup-code > /dev/tty`; у PowerShell використовуйте виведений інсталятором варіант із перевіркою консолі та `[Console]::WriteLine`, не копіюйте код у повідомлення й не записуйте термінал.

Якщо коду немає, клієнт іще не підтримує отримання прав або потрібен запасний спосіб: спершу зареєструйте нік у застосунку на власному сервері. З папки випуску виконайте команду, замінивши `my_nickname` своїм ніком без кутових дужок:

```sh
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml exec backend coco-admin grant-owner my_nickname
```

Це повний варіант `docker compose exec backend coco-admin grant-owner <ник>` для нашого окремого файлу. Утиліта вже є в образі разом із `messenger-server`; Rust на самому ПК для цієї команди не потрібен. Команда не створює облікового запису й видасть `Account not found`, якщо ви зареєструвалися на іншому сервері або вказали інший нік. Вона також відкликає старі сеанси адміністрування.

Оновіть профіль/увійдіть у застосунок знову, відкрийте адміністрування й налаштуйте другий фактор: автентифікатор/TOTP, резервні коди та паперовий ключ відповідно до режиму, запропонованого на екрані. Типово політика передбачає пароль і обидва додаткові фактори; зберігайте паперовий ключ окремо від ПК. Точний поточний екран первинного налаштування **перевірити на телефоні**. Адреса вебконсолі — `https://ИМЯ/administration`; вхід можна відкрити із захищеного розділу застосунку через одноразовий handoff. Знання URL не дає прав. `COCO_ADMIN_KEY` — ключ шифрування факторів сервера, а не пароль входу; його вже створив інсталятор, не замініть його випадково.

У консолі заповніть назву, контакт оператора, обмеження розміру файлу, місця на обліковий запис і загального сховища. У розділі «Власний сервер» власник будь-коли перемикає відкриту реєстрацію та реєстрацію за запрошеннями. Власник і модератори створюють, переглядають і відкликають запрошення; типово код діє 7 днів і використовується один раз. Код і посилання доступні для копіювання/надсилання лише під час створення. Посилання зберігає адресу сервера й код у фрагменті; iOS та Android SH-3 імпортують його після підтвердження адреси. Відкликаний, прострочений або використаний код не підходить. За відкритої реєстрації запрошення не потрібне; тимчасове повне закриття реєстрації залишається окремим налаштуванням.

Власник також бачить перевірку публічного URL, TURN, кімнат, push, доступності bucket, готовності завантажень, вільного місця, версії та міграції. Для перевірки TURN передайте в **backend** `TURN_EXTERNAL_IP`, `TURN_MIN_PORT=49152`, `TURN_MAX_PORT=49200`, що збігаються з coturn; для адреси використовується наявний `PUBLIC_API_ORIGIN`. SH-1 поки передає зовнішній IP лише медіасервісам: інсталятор/compose потрібно узгодити під час об’єднання етапів. Перевірка не встановлює з’єднання з публічним URL/TURN/LiveKit/push і прямо показує `not_probed`: DNS, сертифікат і зовнішні порти перевірте з мобільного інтернету. Запит до bucket — лише HEAD, до 5 секунд. Залиште місце для ОС, бази, образів, журналів і резервної копії: нуль/«Без обмежень» не захищає диск. Докладніше: API (docs/ADMIN_API_CONTRACT.md у репозиторії вихідного коду), консоль адміністрування (docs/COCO_ADMIN_CONSOLE.md у репозиторії вихідного коду), контрольний список для робочого розгортання (docs/DEPLOYMENT_PRODUCTION.md у репозиторії вихідного коду).

### Адреси сервера: серверну частину підготовлено (18 листопада, фаза 1a)

Для картки «Адреси сервера» сервер тепер надає власнику й адміністратору зовнішню HTTPS-адресу, ім’я хоста й окремий порт (зокрема **443**), налаштований зовнішній IP для дзвінків, знайдені домашній IP і порт ПК, порти особистих дзвінків, стан кімнат і тип інсталяції/входу. Картки iOS/Android/web/desktop з’являться окремим етапом; ця гілка готує дані для них. Модератори та звичайні користувачі цих відомостей не отримують. `TURN_EXTERNAL_IP` має позначку «Указано під час встановлення. Зараз не перевірено.»; це не нове вимірювання зовнішнього IP. Самоперевірка не підключається до цих адрес.

ПК заново визначає домашню адресу **під час кожного керованого запуску**: встановлення, повторного встановлення/оновлення, відновлення з резервної копії та запуску такою командою з папки випуску:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\start.ps1
```

```sh
bash scripts/selfhost/start.sh
```

Windows вибирає фізичний інтерфейс маршруту за замовчуванням із найменшою сумою метрик маршруту й інтерфейсу; Docker/WSL/Hyper-V/VPN не стають домашньою адресою. Linux використовує IPv4-адресу джерела з `ip route get` і перевіряє фізичний інтерфейс; потрібні `iproute2`, GNU coreutils і `flock` з util-linux. Якщо відповідної мережі немає, вибір неоднозначний або сталася помилка, стара адреса та час її визначення очищуються: сервер показує, що домашня адреса невідома. Нове значення застосовується через Compose `up --no-build`, за потреби backend створюється заново. Перевстановлення з новими секретами не потрібне.

Інсталятор атомарно змінює лише `UNYRI_LAN_ADDRESS`, `UNYRI_LAN_PORT`, `UNYRI_LAN_DETECTED_AT`, `UNYRI_HOSTING_KIND`, `UNYRI_INGRESS_MODE`, `UNYRI_TUNNEL_PROVIDER`; решта рядків, секрети й права доступу зберігаються. Тип інсталяції за замовчуванням — `unknown`: вкажіть у приватній конфігурації `home_pc` для домашнього ПК або `vps` для дата-центру; за `vps` приватна мережа дата-центру не видається за домашню. Вхід за замовчуванням — `direct`; `tunnel` і провайдери `tailscale_funnel` / `cloudflare` — лише метадані вже налаштованого входу, а не встановлення тунелю.

Для автоматичного запуску разом з ОС використовуйте ці самі команди після готовності мережі й Docker, під обліковим записом, з якого встановлювали сервер. На цьому етапі завдання Windows/служба Linux автоматично не реєструється; це потрібно налаштувати локально й перевірити після перезавантаження. **Прямий `docker compose up`, `start`, `restart` або автоматичний перезапуск контейнера зберігає останнє записане значення** й не визначає нову адресу ПК. Після зміни мережі запустіть керовану команду. Якщо під час завантаження ОС до неї не дійшла черга, збережений час не означає свіжої перевірки. Не використовуйте знайдений IP для небезпечного входу через HTTP: зберігайте HTTPS-ім’я сервера й налаштуйте локальний DNS, не вимикайте перевірку сертифіката. Керівник команди ще має перевірити збирання Rust, роботу реальних інсталяторів, DHCP/перезавантаження та роботу в Linux у цій гілці.

### Android SH-3: два телефони без термінала

1. На першому телефоні відкрийте Налаштування → Сервер, введіть HTTPS-адресу власного сервера й підтвердьте. Адреса вибраного сервера завжди є на картці. У розділі «Власний сервер» прочитайте коротку інструкцію; «Перевірити з’єднання» вручну перевіряє DNS, TLS, публічний API, мінімальну версію застосунку й показує стан уже активного WebSocket. Неперевірені поля не означають успіху.
2. Зареєструйтеся й пройдіть крок із ключем відновлення login2. Після звичайного входу застосунок перевірить, чи можна отримати права власника. Лише якщо це доступно, у розділі «Профіль» поруч із сервером з’явиться «Стати власником».
3. Введіть одноразовий 16-символьний код інсталятора чотирма групами або відскануйте QR, що містить сам код. Регістр і дефіси не мають значення. Після успіху роль оновиться й відкриється наявне налаштування захисту адміністратора. Якщо вичерпано ліміт спроб, зачекайте 15 хвилин і повторіть вручну. На сервері з власником рядка отримання прав немає.
4. У розділі Адміністрування → Власний сервер увімкніть «Лише за запрошенням». За відкритої реєстрації додаткового поля немає. Власник і модератори створюють запрошення (1–10 000 використань, 1–365 днів), бачать статус, кількість використань, термін дії та автора, відкликають із підтвердженням. Налаштування реєстрації та самоперевірка доступні лише власнику.
5. Відразу під час створення скопіюйте або надішліть код/посилання чи покажіть QR другому телефону: повторно сервер код не надає. Посилання має вигляд `https://SERVER/#server=<encoded-origin>&invite_code=<encoded-code>`: код після `#`, ніколи після `?`. На другому телефоні використовуйте QR у Налаштування → Сервер або наявний сканер у розділі «Контакти». Під час відкриття посилання Android без перевіреного домену може запропонувати «Відкрити за допомогою» або залишити його в браузері; тоді використовуйте QR. Перед зміною сервера підтвердьте показану повну адресу; активний обліковий запис іншого сервера вийде із сеансу. Код підставиться в реєстрацію. Не публікуйте посилання з чинним кодом.
6. Вимкніть Wi-Fi на другому телефоні. Перевірте вхід, повідомлення в обидва боки, дзвінок і сповіщення, коли застосунок закрито. Власник відкриває Адміністрування → Власний сервер → Перевірити сервер і читає пояснення кожного поля. `not_probed` означає «перевірте з телефона на мобільному інтернеті»: сервер перевіряє конфігурацію, а не зовнішній DNS/TLS, TURN UDP/TCP, кімнати чи фактичну доставку push. Якщо провайдера push не налаштовано, не очікуйте фонової доставки.

Android SH-3 підготовлено 18 листопада 2026; керівник обов’язково має перевірити два телефони в середовищі QA. iOS отримає ці екрани з новим Mac. Впровадження не змінює вже випущених застосунків автоматично.

## 9. Дзвінки, кімнати й сповіщення

Для особистого дзвінка Coturn надає ретранслятор, а backend — короткочасні облікові дані. Секрет TURN однаковий в обох службах і не передається телефону. Ретранслятор ізольований від бази даних/Redis/MinIO; пересилання до приватних і службових мереж заборонено. Перевіряйте звук/відео між **різними зовнішніми мережами**, а не лише двома телефонами в одній мережі Wi-Fi.

LiveKit вмикається відповіддю `y` під час першого встановлення (профіль `rooms`). Він використовує вказаний публічний IPv4, 17881/TCP і 17882/UDP; API 7880 залишається всередині Docker. `room.auto_create=false`, а кожне публічне з’єднання `/rtc` проходить авторизацію в backend. `/twirp/*` закритий для зовнішнього доступу. Див. [наявну схему кімнат](../scripts/conference/README.md). **Перевірити** отримання/розшифрування аудіо/відео двома реальними клієнтами; HTTP health цього не підтверджує. Якщо кімнати не вибрано, особисті повідомлення й особисті дзвінки не залежать від LiveKit.

Офіційний застосунок на новому сервері отримує повідомлення через відкрите з’єднання. Фонові сповіщення та вхідні дзвінки, коли застосунок у режимі сну або вивантажений із пам’яті, **не гарантуються**: спільного ретранслятора push ще немає. APNs alert/VoIP уже реалізовано в сервері, але потрібні дозволені ключі Apple для bundle/topic/environment установленого iOS-клієнта; для FCM — обліковий запис служби саме Firebase-проєкту Android-клієнта. Випадково створений ключ іншого проєкту не підійде. Офіційні ключі операторам не надаються. Власні збірки мобільних застосунків можуть використовувати власні налаштування провайдерів, але це виходить за межі встановлення SH-1.

У стеку явно задано `UNYRI_OFFLINE=true`: вимкнено лише надсилання push через провайдерів, а не роботу сервера/інтернету. Ключів push немає, і нічого монтувати не потрібно. Навіть прийнятий провайдером HTTP-запит не доводить, що сповіщення з’явилося на екрані. Поточні обмеження й модель майбутнього ретранслятора: аудит push у повному репозиторії вихідного коду (`docs/PUSH_SECURITY_AUDIT_20261113.md`). Android Force stop і системні обмеження перевіряються окремо. Не намагайтеся «увімкнути push», відкривши ще один вхідний порт.

## 10. Оновлення, резервна копія, перенесення

### Оновлення

Автоматичного оновлення за розкладом немає. Перед оновленням зробіть копію, збережіть саме ту папку попереднього випуску та його образи. Отримайте сумісний випуск сервера/клієнтів, замініть файли перевіреним комплектом, зберігши `.env`, і повторно запустіть `install.ps1`/`install.sh`. На VPS можна повторити команду завантажувача з потрібним `--version`. Інсталятор завантажує образи версії комплекту, показує образ/ID до й після та виконує `up --no-build`; секрети й томи зберігаються. Теги випуску не є незмінними дайджестами реєстру: видавець не повинен перепризначати опубліковані версії. Для локальної збірки знову потрібен `--from-source` / `-FromSource`. Повернення до старого образу після SQL-міграцій допустиме лише за сумісної схеми; інакше відновіть повну попередню копію на окремій машині. Пароль PostgreSQL у наявному томі не змінюється заміною `POSTGRES_PASSWORD` у `.env`.

### Повна холодна резервна копія

Заплануйте коротку перерву й перевірте вільне місце. Виконайте:

```powershell
# Windows, from the release directory:
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\backup.ps1
```

```sh
# Linux:
bash scripts/selfhost/backup.sh
```

Сценарій спочатку отримує невеликий допоміжний образ, потім зупиняє **лише проєкт unyri-selfhost**, архівує шість томів (Postgres, Redis, MinIO, Caddy data/config і приватний backend_data) та `.env`, перевіряє, чи можна прочитати архіви, і знову запускає стек. Папка `selfhost-backups/ДАТА...` з маркером `COMPLETE` вважається завершеною копією. У разі помилки маркера немає; перевірте, чи сервер відновив роботу. Скопіюйте завершену папку разом із вихідним кодом саме того випуску на інший захищений диск; обмежте доступ, адже вона містить особисті дані, сертифікати й секрети. Копія історії на телефоні та серверна резервна копія виконують різні завдання: сервер не відновлює втрачені клієнтські ключі розшифрування.

Старі `scripts/Backup-CocoDatabase.ps1`/`Restore-CocoDatabase.ps1` перевіряють саме контейнер `messenger-postgres` проєкту розробника й для selfhost **не застосовуються**. Наші сценарії зберігають увесь стек, а не лише SQL.

`backend_data` зберігає приватні файли SH-2 (код власника й позначку про його показ), монтується в `/app/data` із власником UID 10001 і входить до шостого архіву `backend_data.tgz`. Не виводьте вміст файлів або архівів у журнали. Видалення через `down --volumes` видаляє також цей том; старі копії з п’яти томів потребують окремого плану міграції перед відновленням новим сценарієм.

### Відновлення або перенесення на інший ПК

Використовуйте **новий Docker Engine без томів `unyri-selfhost_*`**, наприклад окрему VM. Це захищає наявну інсталяцію: сценарій відновлення відмовиться працювати, якщо будь-який цільовий том уже існує. Для аварійного відновлення на тому самому ПК спочатку збережіть пошкоджені томи й використовуйте окремий Engine; сценарій відновлення їх не видаляє.

1. Установіть Docker, розпакуйте вихідний код **того самого випуску**. Перенесіть завершену копію, наприклад у `E:\UNYRI-backup` або `/mnt/backup/unyri`. До першого запуску інсталятора скопіюйте з неї `.env` у корінь папки випуску. Не генеруйте нових секретів.
2. Виконайте відновлення, указавши фактичну папку копії:

```powershell
Copy-Item -LiteralPath E:\UNYRI-backup\.env -Destination .env
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\restore.ps1 -BackupPath E:\UNYRI-backup
```

```sh
install -m 600 /mnt/backup/unyri/.env .env
bash scripts/selfhost/restore.sh /mnt/backup/unyri
```

3. Після успішного відновлення під час перенесення змініть `TURN_EXTERNAL_IP` і DNS A/DDNS на нову публічну IP-адресу. Збережіть попереднє доменне ім’я: origin бере участь у розділенні клієнтських даних. Перехід на інше ім’я не означає автоматичного перенесення облікових записів у клієнтах. Якщо змінюєте підмережу Docker через конфлікт, узгоджено змініть `UNYRI_SUBNET`, `UNYRI_PROXY_IP`, `UNYRI_SFU_IP` і `CONFERENCE_LIVEKIT_API_URL` (якщо кімнати ввімкнено).
4. Зупиніть старий сервер, перш ніж спрямовувати користувачів на новий. Запустіть звичайний інсталятор на новому сервері, перевірте health, вхід в обидва облікові записи, старе вкладення й нове повідомлення/фото/дзвінок. Лише після перевірки копії можна планувати нове оновлення. У разі помилки збережіть частково відновлені томи й з’ясуйте причину; не об’єднуйте дві бази даних.

### Зупинення або видалення

З папки випуску:

```sh
# Stop/remove containers and networks, keep data:
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml down
# Permanent deletion of this stack's SIX volumes: ONLY after checking an independent backup:
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml --profile rooms down --volumes
```

`down --volumes` безповоротно видаляє дані інсталяції; для оновлення ця команда не потрібна. Потім видаліть лише цю папку випуску та її приватний `.env`, якщо сервер більше не потрібен; незалежну копію зберігайте за власними правилами. На Windows видаліть наші правила:

```powershell
Get-NetFirewallRule -Name 'UNYRI-Selfhost-*' -ErrorAction SilentlyContinue | Remove-NetFirewallRule
```

На роутері видаліть лише створені для UNYRI ручні/UPnP-правила. У Linux видаліть відповідні дозволи `sudo ufw delete allow 80/tcp` й аналогічно для решти рядків таблиці, **якщо вони не потрібні іншим службам**. Видаліть записи DDNS/updater для цієї інсталяції та хмарні правила. Не використовуйте `docker system prune --volumes` для видалення однієї інсталяції.

## 11. Якщо не працює

Почніть із безпечних команд; не публікуйте `.env`, повний вивід `docker compose config` або `docker inspect` зі змінними середовища:

```sh
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml ps -a
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml config --quiet
docker compose --project-name unyri-selfhost --env-file .env -f docker-compose.selfhost.yml logs --tail 80 backend caddy coturn
```

Журнали переглядайте локально: перед надсиланням вилучіть токени, адреси користувачів і особисті дані. Caddy access-log навмисно не ввімкнено: підписані S3/room URL не повинні потрапляти до спільних журналів. Щоб переглянути список локальних портів:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\selfhost\check-ports.ps1 -Domain family.example.org
```

```sh
bash scripts/selfhost/check-ports.sh
```

| Ознака | Що зробити |
|---|---|
| Docker відсутній/Engine недоступний | Установити вручну/запустити Docker Desktop або Engine; перевірити Linux containers і локальний context. Жодних даних видаляти не потрібно |
| Збирання/завантаження не завершилися | Перевірити інтернет, вільне місце, доступ до GitHub/Cargo/Go/registry. Повторно запустити інсталятор; не видаляти `.env`/томи |
| Address already in use | Порт зайнятий іншою службою. Знайти її через check-ports; не зупиняти невідому службу автоматично |
| Pool overlaps with other one | Конфлікт підмережі Docker. Вибрати вільну й узгоджено змінити чотири налаштування з розділу про перенесення |
| Локально працює, через мобільний інтернет — ні | Порівняти WAN/публічний IPv4, A/AAAA, перенаправлення портів, брандмауер ПК/хмари, CGNAT. Перевірка TCP не підтверджує роботу UDP |
| Через мобільний інтернет працює, удома через домен — ні | Перевірити NAT loopback/локальний DNS. Не змінювати домен на HTTP/LAN IP в обліковому записі |
| Помилка сертифіката | Перевірити домен, годинник ПК/телефона, DNS, вхідні 80/443 і журнали Caddy. Не обходити перевірку TLS. Після виправлення дати Caddy повторити видачу; не видаляти том сертифікатів заради спроби |
| Інсталятор повідомив local ready, але public health failed | Стек продовжує працювати; виправити DNS/TLS/маршрут. Перевірити через мобільний інтернет: LAN hairpin може заважати лише перевірці з ПК |
| Health зелений, фото/файл не надсилається | Перевірити storage-init (Exited 0 очікується), приватний bucket, write-only principal, Caddy S3 path/Host і квоти. Ніколи не вмикати версіонування bucket: навіть Suspended не підтримується |
| Дзвінок без звуку/не з’єднується | Перевірити 3478 UDP/TCP, увесь діапазон UDP ретранслятора, актуальність TURN_EXTERNAL_IP і DDNS. Перевірити у двох зовнішніх мережах; закритий UDP потребує іншої схеми TURN/TLS |
| Кімнати не працюють | Перевірити `COMPOSE_PROFILES=rooms`, усі чотири налаштування CONFERENCE, поточну публічну IP-адресу, 17881/TCP+17882/UDP і gateway. Не відкривати зовнішній доступ до 7880/Twirp |
| Немає push, коли застосунок закритий | Це очікуване обмеження офіційних клієнтів до появи ретранслятора push; додаткові вхідні порти його не усунуть |
| Команда адміністратора не знаходить обліковий запис/не дає ввійти | Звірити нік та вибраний у застосунку сервер; оновити профіль, пройти перевірки за факторами автентифікації. Відновити початковий COCO_ADMIN_KEY зі своєї копії, не генерувати заміну |
| Немає місця | Звільнити місце поза даними встановлення, обмежити квоти/зробити резервну копію. Не видаляти томи Docker, щоб «очистити кеш» |

Для перевірки TCP **через інше підключення до інтернету**: `Test-NetConnection family.example.org -Port 443`, потім 3478 і, якщо ввімкнено кімнати, 17881. 80 можна перевірити через перенаправлення HTTP. UDP перевіряйте справжнім TURN-дзвінком/авторизованим тестером TURN: перевірки TCP або сайту «порт відкритий» недостатньо. Запишіть випуск, ОС, час, ознаку проблеми й етап; пункти, залишені як «перевірити», перелічено у звіті SH-1.
